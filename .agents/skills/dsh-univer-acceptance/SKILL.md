# DSH × Univer 真实环境验收

从用户指定的 DSH 桌面端或 Web Profile 操作。默认分别验收 Sheet、Doc、Slide 的基本功能。用户指定类型或环节时，按指定范围执行；进阶项按改动和风险选择。

## 1. 确定范围和通过条件

按用户实际会做的事选择场景。对每种格式，先写下首轮应看到的内容、第二轮要修改的位置，以及一处应保留的内容。从发起请求到看到最终成果，尽量沿用同一份样本。实机验收关注已安装产品的使用体验；导入导出兼容性、格式往返保真等技术细节由对应的自动化测试维护。[格式交换测试](../../../test/integration/exchange.test.ts)

### 基本功能（默认覆盖三种格式）

| 功能点 | 用户可观察的通过条件 |
| --- | --- |
| 主动发现与创建 | 新会话中只描述办公需求，Agent 自行找到插件、成功调用工具，并创建所需类型的文档。 |
| 实时浮窗 | 自动预览开启时，修改过程中出现对应文件的浮窗，能看到本次任务的内容和状态。 |
| 底部审阅卡片 | 提交审阅并结束回合后，浮窗收起，底部卡片显示对应草稿和“待确认”。折叠再展开，内容仍可见。 |
| 二次修改 | 在同一会话提出修改后，Agent 接着编辑原草稿；最新卡片中可见新结果，应保留的内容仍在。 |
| 用户确认合入 | 用户明确要求验收合入时，从最新卡片确认后，两轮卡片均显示“已合入”。从文件入口重开当前版本，能看到第二轮修改。 |
| 文件交付 | 从会话里的文件入口找到并打开用户要求的 Excel、Word 或 PowerPoint 文件，确认是本次交付的内容。 |

### 进阶功能（按请求或改动选测）

| 功能点 | 用户可观察的通过条件 |
| --- | --- |
| 对比与版本选择 | 从审阅卡片切换“查看／对比”，能辨认比较双方，并找到本次改动。要验收局部差异，选用已有主线内容的临时样本。 |
| 浮窗交互与输入焦点 | 预览自动打开时仍能在聊天框连续输入；折叠、全屏或恢复浮窗后，仍能找到原文件并继续当前任务。 |
| 多文件与多会话 | 两个会话分别修改具有明显差异的文件，来回切换时，浮窗、卡片和文件入口指向各自的成果。 |
| 预览偏好与文件树 | 分别切换自动浮窗或卡片设置，观察对应入口是否生效；从文件树仍能按需打开文档。测完恢复用户原设置。 |
| 放弃草稿 | 用户明确要求验收丢弃时，在临时样本中放弃一份待审修改。卡片显示“已丢弃”，重新打开主线可见原内容。 |

## 2. 确认环境，建立临时工作区

- 记录目标 DSH 版本、Profile、插件版本和构建 commit。桌面端可能自带另一版 CLI，安装时用与目标应用配套的启动器；可从启动器的 `--version` 和目标 Profile 的 `package.json` 核对。浮窗与审阅卡片还受该 Profile 的用户偏好控制，记录实际开关。
- 需要验收本地安装包时，从目标 checkout 运行 `bash scripts/build-dist.sh`，把这次生成的 `dist/dsh-univer-office-<version>.tgz` 复制到持久目录，文件名带 commit，以区分相同插件版本的多次构建。用目标启动器运行 `dsh plugin --profile <profile> add <tgz 的绝对路径>`。正常重启对应应用，再对照安装目录中 `node_modules/dsh-univer-office/lib/build-info.json` 的 commit 和源码的 `git rev-parse HEAD`。[构建与发布](../../../docs/operations/build-and-release.md)

每次验收在系统临时目录中新建专用目录，记录其绝对路径。例如运行以下命令，使用打印出的路径在 DSH 添加测试工作区：

```sh
python3 -c 'from pathlib import Path; import tempfile; print(Path(tempfile.mkdtemp(prefix="dsh-univer-acceptance-")).resolve())'
```

Sheet、Doc、Slide 各开一个全新会话，发送第一条提示前确认工作区选择器指向本次目录。同一样本的第二轮沿用原会话。样本、导出文件、截图和临时诊断文件都写在该目录内；需要已有文档时，先复制一份到临时目录后再操作。安装步骤中供 Profile 长期引用的包仍放在持久目录。

## 3. 首轮创建，观察工具发现与预览

用日常办公语言描述受众、输入数据、所需内容和交付物。把插件名、工具名、技能名、原生文件后缀和内部状态留在验收记录中。用目标 Profile 的正常设置发起任务，让 Agent 自行选择工具。

发出请求后立即看浮窗，记录它何时出现、指向哪个文件，以及能否看到首轮预期内容。待回合结束，在底部卡片核对文件、状态和内容。在会话轨迹中记录首次相关工具调用、成功或失败结果，以及返回的文件、worktree 和 Unit 标识。[工具披露与技能路由](../../../docs/modules/agent-integration.md)

如果其他方式也生成了 Office 文件，分别记录交付结果和插件发现结果。若 Agent 已选中插件但调用报错，记录具体失败步骤。保留首次轨迹，后续点名工具的排障可另行记录。

## 4. 在原会话修改并审阅

以用户身份提出一处可辨认的修改。在浮窗或最新卡片中找到对应的单元格、段落或幻灯片，核对新结果和应保留的内容。若显示旧值或打开了其他文档，再用两轮轨迹中的文件、worktree 和 Unit 标识定位问题。[Client 预览与审阅](../../../docs/modules/client-preview-and-review.md)

## 5. 从用户入口核对最终成果

从会话交付入口打开 Office 文件，按导出时刻核对本次样本的关键内容。若用户明确要求验收合入，从最新卡片核对文件和草稿名称，完成合入确认后，从 DSH 文件树重新打开当前版本，核对第二轮修改。只有发现不一致时，才按需回读文件或检查工具结果以定位原因。

## 6. 清理并报告

通过、失败或中断时都执行收尾。先记录证据，按用户要求将需保留的文件复制到约定位置并核对副本。待写入停止，关闭本次预览，移除本次添加的临时工作区入口。核对目录正是创建时记录的绝对路径后再删除，确认路径已不存在。保留 Profile 引用的安装包及用户原有工作区；若有残留，说明路径和原因。

交付时注明 DSH 版本、Profile、插件构建和清理结果。以功能点为行、文档类型为列，逐项标明通过、失败、未执行或不适用。失败项给出预期、实测、失败步骤及相关工具结果。只有实际看过的界面才报告目视通过，错过浮窗则注明该项未观察到。

## 任务设计示例（可替换）

下表只示范如何把用户需求变成可核对的两轮操作。题材、数据、结构和预期值均可按本次改动替换。

| 格式 | 首轮用户请求举例 | 次轮用户请求举例 | 验收者可核对的结果 |
| --- | --- | --- | --- |
| Sheet | 给财务做一份 Excel 采购表。铅笔 3 支，每支 8 元；笔记本 2 本，每本 15 元。小计和合计随数量自动更新。 | 铅笔改成 5 支，帮我看看新的总额。 | 铅笔小计 24 → 40，总计 54 → 70；笔记本小计仍为 30。 |
| Doc | 给项目组写一页 Word 通知，标题“交付通知”加粗。正文分两段写交付日期是周三、负责人是林青。 | 交付改到周五，其他内容保留。 | 正文日期更新，负责人段落和标题加粗样式保留。 |
| Slide | 做两页例会用的 PowerPoint。首页写“项目简报”，第二页标题为“交付计划”，用蓝色矩形标出“周三交付”。 | 把第二页矩形里的字改为“周五交付”。 | 回到第二页可见新文字，矩形颜色、位置及首页内容保留。 |
